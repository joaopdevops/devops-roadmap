**Lab 2.5 — Static Routing (last lab of Month 01)**
- Built the topology in Packet Tracer: two `/24` networks (buildings A and B), each behind its own router, joined by a `/30` point-to-point link (the "road"). `/30` because a point-to-point link only has two ends — block of 4, two usable addresses, exact fit.
- Addressed every interface via Cisco IOS CLI and confirmed `up up` on `show ip interface brief`.
- **Ping without a route failed on purpose** — and failed the *informative* way: `Reply from 192.168.1.1: Destination host unreachable`. The gateway itself answered, meaning the packet reached the router and the router had no matching route. That ICMP message is Lab 2.4 showing up inside Lab 2.5.
- Added static routes **in both directions**, then ping came back **4/4, 0% loss, TTL=126** — 128 minus 2, one decrement per router: independent proof the packet crossed both.

**Key concept — connectivity ≠ knowledge**
The `/30` road was up the whole time (`C 10.0.0.0/30 is directly connected`). The static route didn't build a road; it **taught the path**. A router only knows what is plugged directly into it — for R1, the world ended at the far end of the link. Routers don't gossip: without a routing protocol they exchange nothing. Two ways to learn the rest: write it by hand (`S`, static) or let a protocol do it (`O`, `D`, `B` — Month 02). With 2 routers, by hand is trivial. With 200, it isn't.

**Three mistakes, and how I found them**
1. `ip route` typed outside `configure terminal` — no `S` line appeared. The **prompt is the indicator**.
2. `show ip route` typed in the PC's command prompt → `Invalid Command`. IOS commands don't exist there.
3. PC1 addressed as `192.168.20.1` instead of `192.168.2.10` — cost ~25 minutes of `Request timed out` with both routes already correct. **I diagnosed this one myself** by reading `ipconfig` on PC1.

**The troubleshooting table that solved it:** `Destination host unreachable` from the gateway = the router has no route (the *outbound* path is broken). `Request timed out` = outbound worked, the *reply* got lost (missing return route, or the destination host itself). The symptom changing from one to the other is measurable progress, not trial and error.

**Why it matters for DevOps:** missing/incorrect routes are the number one cause of "my service can't reach the other one" — AWS VPC route tables, VPC peering, Kubernetes pod-to-pod across nodes. Golden question when one side is up and still won't connect: **is there a route in both directions?**

**Lab 2.5 — Rota estática (último lab do Mês 01)**
- Topologia montada no Packet Tracer: duas redes `/24` (prédios A e B), cada uma atrás do seu roteador, ligadas por um link ponto a ponto `/30` (a "estrada"). `/30` porque link ponto a ponto só tem duas pontas — bloco 4, dois endereços úteis, encaixe exato.
- Endereçamento de todas as interfaces pela CLI do Cisco IOS, com `up up` confirmado no `show ip interface brief`.
- **Ping sem rota falhou de propósito** — e falhou do jeito *informativo*: `Reply from 192.168.1.1: Destination host unreachable`. Quem respondeu foi o próprio gateway, ou seja: o pacote chegou no roteador e o roteador não tinha rota que casasse. Esse ICMP é o Lab 2.4 aparecendo dentro do Lab 2.5.
- Rotas estáticas adicionadas **nos dois sentidos** e o ping voltou **4/4, 0% de perda, TTL=126** — 128 menos 2, um decremento por roteador: prova independente de que o pacote atravessou os dois.

**Conceito central — conectividade ≠ conhecimento**
A estrada `/30` esteve de pé o tempo todo (`C 10.0.0.0/30 is directly connected`). A rota estática não construiu estrada nenhuma; ela **ensinou o caminho**. Um roteador só conhece o que está plugado diretamente nele — pra o R1, o mundo acabava na ponta do link. Roteador não fofoca: sem protocolo de roteamento, eles não trocam nada. Dois jeitos de aprender o resto: escrever na mão (`S`, estática) ou deixar um protocolo fazer (`O`, `D`, `B` — Mês 02). Com 2 roteadores, na mão é trivial. Com 200, não é.

**Três erros, e como achei cada um**
1. `ip route` digitado fora do `configure terminal` — nenhuma linha `S` apareceu. O **prompt é o indicador**.
2. `show ip route` digitado no prompt do PC → `Invalid Command`. Comando de IOS não existe ali.
3. PC1 endereçado como `192.168.20.1` em vez de `192.168.2.10` — custou ~25 minutos de `Request timed out` com as duas rotas já corretas. **Esse eu diagnostiquei sozinho**, lendo o `ipconfig` do PC1.

**A tabela de troubleshooting que resolveu:** `Destination host unreachable` vindo do gateway = o roteador não tem rota (a **ida** está quebrada). `Request timed out` = a ida funcionou, a **resposta** se perdeu (falta rota de volta, ou o problema é o host de destino). O sintoma mudar de um pro outro é progresso mensurável, não tentativa e erro.

**Por que importa pra DevOps:** rota faltando ou errada é a causa nº 1 de "meu serviço não alcança o outro" — route tables de VPC na AWS, VPC peering, comunicação entre pods de nós diferentes no Kubernetes. Pergunta de ouro quando um lado está de pé e mesmo assim não conecta: **existe rota nos dois sentidos?**
